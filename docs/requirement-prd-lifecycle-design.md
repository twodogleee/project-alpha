# 需求评审、人工基线与 PRD 实现设计

日期：2026-10-13。作者：Andersen。范围：生命周期阶段 B，单用户桌面工作空间。状态：已实现并完成验证。

## 产品规则

交付仍由需求版本承载。项目、会话、业务版本与保存记录的关系不变。第一阶段已有范围原文保留，不冒充结构化已确认需求；初次进入正式评审时把范围作为一项待编辑需求，验收标准留空，必须人工补充。

版本详情增加“需求评审”和“PRD”两个产物页。评审包括正式需求候选（名称、正文、验收标准、确认）、澄清问题（阻塞性、结论、延期理由）、设计建议（接受/拒绝/延期及理由）。建议接受后由后端新增一项待确认需求，接受不代表需求已确认。改动需求正文或验收标准会取消该项确认，需先保存变更，再确认；新条目首次保存也保持待确认。

评审基线门槛：范围和目标非空；至少一项需求；所有需求有正文与验收标准且已确认；阻塞问题全部解决；延期问题有理由并明确非阻塞；建议全部处理；评审对应当前范围。保存、生成、下载均不通过门槛。

新问题在界面默认阻塞，API 必须明确提交 blocking，不接受遗漏字段静默变为非阻塞。PRD 已知联调模板占位章节也属于定稿阻塞项，不能仅通过清空待确认清单绕过内容完善。

用户明确点击“确认评审基线并进入 PRD”，服务器校验当前保存修订后保存不可变基线、推进阶段。基线包含当时的版本名称、目标、范围、评审内容、来源修订与时间。确认命令幂等，跨窗口修改返回冲突。

PRD 包含背景、目标、范围、业务流程、业务规则、异常路径、验收标准、非功能边界与排除范围，并记录覆盖的需求 ID。手工编写和模型生成均允许；本地模板明确标注未调用模型。生成任务持久化，结果先作为候选，显式应用并保存才成为编辑产物。PRD 必须引用具体评审基线，确认要求九个必要章节齐全、覆盖基线全部需求、待确认事项全部处理且上游有效。模型未知规则单独写入 unresolvedIssues，本地模板同样保留待补充事项，不因章节非空自动定稿。

“确认 PRD 基线”进入原型阶段等待接入，版本仍 ACTIVE。原型、开发与验收本轮不实现，不提供伪完成按钮。

## 上游变更

基线确认后对应评审只读。要改动范围或正式需求，先填写原因“重新评审需求变更”，回到 REVIEW 并清除当前确认指针；旧基线、旧 PRD 和历史保存记录保留。PRD 仍保留原基线引用，显示需要同步，不能继续确认。

重新评审后，新需求基线有新 ID。用户可以基于新基线重新生成 PRD，或显式确认采用新基线并人工合并旧文档；不静默改写旧 PRD。模型候选记录生成时基线与 PRD 保存编号，旧结果不能覆盖新修订。只改版本显示名称不重新评审；目标或范围改动必须在 REVIEW 阶段进行。已取消/归档对象只读。

## 数据与服务

新增 V5，不修改已执行 V1–V4。版本阶段允许 REVIEW/PRD/PROTOTYPE。新增生命周期当前状态、产物保存记录、不可变基线、PRD 生成任务四张表；结构化内容按有界 JSON 文本保存，关系、修订、任务状态和基线来源独立字段维护。基线通过同版本复合外键关联，禁止引用其他版本基线。

LifecycleService 管理评审、门槛、基线和上游失效；LifecycleRepository 使用 MyBatis Plus。沿用短事务项目根锁、expectedRevision、统一安全响应；模型调用在事务外。PRD 任务引用固定基线，记录实际模式/模型，重启将未结束任务标记中断，失败不退回模板。没有 Graph 检查点恢复或跨实例调度。

## 交互与验证

评审页显示确认进度、阻塞门槛、独立条目和人工确认按钮。PRD 页显示来源基线、草稿/已确认/需要同步状态，编辑章节、生成候选、保存记录和确认按钮。历史只读，下载区分草稿与已确认基线，未保存内容不可下载成正式稿。未保存输入、路由切换和冲突继续使用工作空间保护。

验证覆盖新需求/正文变更撤销确认、建议接受不自动确认、阻塞与延期门槛、两类基线幂等与不可变历史、跨版本来源拒绝、PRD 覆盖与上游失效、生成候选竞争、任务失败/重启、取消只读、真实 PostgreSQL V4→V5 迁移以及桌面浏览器完整阶段转换。

## 接口契约

统一前缀 `/api/alpha/workspace/versions/{id}/lifecycle`，响应仍为 `{code,message,data}`，基线和产物独立于版本主体 revision。

| 方法/子路径 | 业务命令与参数 |
| --- | --- |
| GET 根路径 | 当前评审/PRD、产物锁、有效基线、服务器门槛与近期任务 |
| PUT review | expectedRevision、结构化 review；服务器撤销新增/变更确认 |
| POST review/confirm | expectedRevision、sourceRevision、requestId；确认并进入 PRD |
| POST reopen | expectedRevision、expectedVersionRevision、reason；保留历史并重开评审 |
| PUT prd | expectedRevision、sourceBaselineId、可空 sourceRunId、九章节和 requirementIds/unresolvedIssues |
| POST prd/confirm | expectedRevision、sourceRevision、requestId；确认并进入原型等待 |
| POST prd/runs | expectedRevision、baselineId、requestId；202 持久化候选任务 |
| GET prd/runs/{runId} | 任务归属校验和安全终态，不返回凭证/模型上下文 |
| GET baselines[/{baselineId}] | 不可变基线分页或指定正文，校验同版本来源 |
| GET history?kind=REVIEW/PRD/EVENT&page=1 | 只读保存记录和重新评审原因，每页 50 |

评审/PRD 当前副本采用独立聚合锁，未保存副本不会在任务轮询时刷新基准。正文总 JSON 文本上限 120000 字符，需求、问题和建议各最多 100 项，PRD 待确认事项最多 30 项。长于单条需求 12000 字符的旧范围不会强塞成一条需求，需人工拆分；原文完整保留于版本。

范围和目标的指纹用于基线有效性，版本显示名称改动不失效。所有写入仍锁项目根，阶段/基线/范围修订原子推进。事件记录保留重新评审原因，历史下载不引用当前未保存输入。当前初次读取会初始化未确认评审与首份保存记录，既不调用模型也不确认内容。

当前 PRD 的覆盖集合记录需求 ID，候选必须且只能覆盖已确认基线的全部需求。手工采用新基线是明确命令，保存前需逐章人工合并；基线链不会静默切换。

## 失败提示与诊断日志

PRD 区域只突出显示最新任务的失败或中断。提示可关闭，轮询不会再次展开同一条已关闭提示；开始新的生成或生成成功后收起旧提示，新的失败仍显示。近期失败任务保留在默认折叠的“生成失败记录”中，包含任务编号和安全错误说明，不删除服务端记录，也不自动重试历史基线。

模型客户端在异常离开调用边界前，使用当次凭证提取并脱敏 HTTP 状态、错误代码和平台原因。任务捕获异常后记录关联任务/版本/基线、耗时、分类、脱敏原因和有界代码位置，再写入带诊断编号的失败终态。无法分类的异常不输出任意异常消息。数据库故障导致失败终态无法保存时，仍记录第二次存储故障，不由执行器静默吞掉。

参考 Zero 的日志滚动思路，保留 Alpha 已有 SLF4J/Logback，实现控制台和 `logs/app.log` 文件输出；按日期和 100 MB 滚动，归档保留 3 天、总量上限 1 GB。`ALPHA_LOG_DIR` 允许修改后端日志目录。日志配置和 Java 修改需重启后端；历史失败任务不补造诊断编号。
