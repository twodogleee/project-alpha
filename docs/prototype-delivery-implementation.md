# P6 原型版本与交付实现

日期：2026-10-29。作者：Andersen。对应 [第一阶段设计](prototype-phase-one-design.md) 的 P6，承接 [P5 工作台](prototype-workbench-implementation.md)。

## 操作与状态

历史面板选择修订后，“恢复为新修订”展示目标修订、来源状态和完整页面范围。提交会追加不可变修订，以操作前当前稿为 `parentRevisionId`，以所选历史为 `restoredFromRevisionId`；复用原来源、模板、模型模式及已经验证的文件，`sourceRunId` 为空。恢复不会调用模型，也不会继承目标修订的人工确认。旧来源可能仍为 `STALE`，需要采用最新需求时另行执行“按最新 PRD 更新”。

“确认与导出”面板提供确切范围核对、人工确认及两种 ZIP 下载。人工确认需要绑定当前修订、当前有效 PRD 定稿和该修订完整冻结范围，并经用户明确勾选。原型只覆盖 PRD 子集时，确认也只覆盖这个子集；不能将其显示为整个文档交付完成。

确认资格同时检查：当前有效的 `BASELINE` 来源、`CURRENT` 输入指纹、无未解决 PRD 事项、范围与计划及 `IMPLEMENTED` 覆盖一致、无计划缺口、平台逐页路由/重置/运行错误检查通过、声明的补充交互用例通过、无项目执行中任务。`plan.gaps` 没有可靠的已解决字段，任何非空业务假设或缺口均阻止确认；不能相信模型自行填写 `blocking:false`。浏览器检查不替代人的需求核对。

当前有效确认显示“原型已确认，开发与验收未接入”。生成、下载和恢复不会创建确认记录。当前稿或有效 PRD 基线变化后，旧确认继续保存在历史中，当前状态返回草稿。确认不会将版本推进到开发、验收或已完成状态。

## 事务与接口

本轮沿用 P3 已有表及同聚合约束，不增加迁移。恢复使用 `prototype_commands(kind=RESTORE)`；确认使用 `prototype_confirmations`，并更新聚合的最近确认引用。确认历史与修订历史独立分页。

| 方法与工作空间路径 | 作用 |
| --- | --- |
| `POST versions/{v}/prototype/restore` | 恢复历史为新修订，返回 `Applied` |
| `POST versions/{v}/prototype/confirm` | 人工确认，返回 `ConfirmationView` |
| `GET versions/{v}/prototype/confirmations?page=1` | 当时的精确修订、PRD 定稿及范围 |
| `GET versions/{v}/prototype/revisions/{r}/export?format=source\|static` | 指定修订的 ZIP；错误仍使用 JSON 契约 |

恢复命令携带 `requestId`、`targetRevisionId` 和原型/版本/生命周期/PRD 四种修订锁。确认命令另固定 `revisionId`、`prdBaselineId` 和 `scope`。完整原始命令参与幂等摘要；先校验稳定归属和读取资格，再查幂等，最后检查可变锁。相同命令重放返回原结果，不能把后来的当前指针恢复到旧值；相同请求 ID 改变任一目标、范围或锁则冲突。

完整文件核验在事务外完成，提交时在既有项目根锁内重新检查归属、可写性、执行互斥、四锁与冻结证据。文件损坏或验证证据不一致时拒绝，不以另一份可用产物替代。前端响应未知时保存完整原命令，阻止相关切换，重试不会换请求 ID 或刷新命令里的锁。

归档或取消后仍可只读查看和导出；写入动作拒绝。文档回收后原型读取和导出不可访问，恢复文档后沿用相同修订和文件引用。

## 导出与复现

导出先检查修订归属、全部产物身份和逐文件 SHA-256，再取得有界内存快照；下载前复核文档读取资格。ZIP 按文件流式写出，下载单槽以及 80 MiB 压缩输出限制避免并发积累。断开或失败释放槽，不保存导出任务、确认或新修订。

源码包 `source/` 保留封存的完整模板、生成区、模拟数据、`package-lock.json` 及来源文件，文件字节与该修订一致。静态包 `dist/` 使用确切的已验证产物。两种包提供 `export-manifest.json`、冻结 PRD、归属说明和 HTTP 启动脚本。清单包含修订/恢复链、来源范围、工具链、模式、验证报告和逐文件摘要；历史确认记录明确不等于当前有效确认。

新修订的源码按包内 README 安装锁定依赖，再使用本机 Node 与 Vite 重建。旧镜像修订保留原重建方式。重建静态文件和运行浏览器验收是独立步骤。

静态包必须通过所附 HTTP 服务打开，不能用 `file://`。生成页面继续处于受限 iframe，业务数据只在内存中模拟；导出没有连接真实业务后端或授予生产部署能力。

真实文件浏览器回归发现并修复了 JSON 大小字段的数据库往返差异：`LongNode` 写入后读回可能是 `IntNode`。冻结证据与现场证据现在统一 JSON 表示再逐字段比较，数值、类型、删字段或加字段仍会拒绝；没有缩减摘要核验和证据核对范围。

首次真实模型试验已生成并编辑成功，但验收 PRD 对空白名称的含义不明确，模型将其列入 `plan.gaps`，因此完整交付验收失败。随后补充名称 trim 与容量取值规则后重新验收；没有移除阻塞项来制造通过。

验收后已关闭隔离服务，短时预览地址不再作为交付链接。

独立包复核使用 `scripts/verify-prototype-export.py`，先核对 ZIP 完整清单、安全路径、所有文件摘要及指定封存对象，才写入全新的解压目录。源码按包内 `rebuild.mjs` 构建后，`prototype-worker/test/export-browser.mjs` 对静态包和重建包分别启动所附服务，用真实浏览器逐页访问、执行同一组受限交互用例并检查隔离；不会把模型用例文字当脚本执行。

真实模型最终验收在 2026-10-29 16:13:42–16:18:40（Asia/Shanghai）完成。首次生成有 10 个通过检查，页面修改有 11 个通过检查，计划缺口与确认阻塞均为空。恢复形成 r3，引用 r1 的来源与文件，父修订为 r2；先前 r2 的确认保留，r3 重新调用人工确认接口，版本仍为 `PROTOTYPE`。这是自动验收对人工命令的调用，不是替用户确认现有业务项目。

验收的源码包和静态包包含设备列表、列表内编辑表单与详情，查询、取消、名称校验、容量 `0` 和停用 `false`、保存后跨页同步均有实际浏览器验证；不代表任意 PRD 的业务语义或真实数据系统已验收。

桌面独立包验收使用 `--window-size=1440,1000` 配合 `viewport:null`，报告记录实际内容视口与 iframe 尺寸。本机 Chrome 156 的实际内容视口为 1440×913、iframe 为 1440×849。最初 Playwright 1.58 的视口仿真与 Chrome 156 组合会把 iframe 底部按钮点击送给父 iframe，真实窗口与 Chromium 148 对照均正常；因此改正验收器的窗口配置后，用原源码、原 CSS 和正常点击重跑全部四包通过。没有强制点击、调用业务函数、关闭隔离或修改封存产物。

依据以上业务事务、工作台、真实模型及独立包证据，P1–P6 的第一阶段原型交付闭环已实现并验收。开发、真实业务接口、生产发布与最终业务验收继续属于后续阶段。

## 运行边界

本轮不提交 Git、不迁移或写入现有业务数据、不部署或重启用户现有服务。真实模型验收只读取当前启用的模型配置并在随机 PostgreSQL schema 内执行，结束后删除隔离 schema。任务持久化仍不等于 Graph 检查点恢复；重启继续采用任务中断和显式重试。
